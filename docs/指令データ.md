# 指令データ

日本の二次②の実指令は一般公開されていないため、海外市場の公開データから指令にあたる波形を作る。
基準値と入札の上げ幅・下げ幅はこちらの入札器で決める。どの集合も日本の実運用の指令を再現したものではない。

## 選ぶ条件

load-following型の指令は、EV-VPPにとって難しいと考えられるものを、各国の調整力・需給調整の市場から選ぶ。次の条件をすべて満たすものを使う。

1. エネルギー収支が0にならない
2. AGC型のように、短い周期で上下に振れるものではない
3. 指令が比較的頻繁に来る
4. 系統全体への指令ではなく、個々の入札（資源）への指令である
5. 上げと下げの両方がある
6. 指令の間隔が5分程度
7. 複数の季節にわたって、数千日分の日数がそろう

これとは別に、エネルギー収支が小さいAGC型の比較用として、PJMの調整力信号RegDを使う（`pjm_regd`）。RegDは上の条件1と2を満たさない。

## 何を指令として取り出すか

二次②では、送配電事業者が上げ・下げの指令量を送り、リソースは「ゲートクローズまでに出した基準値 + 指令量」を出す。取り出すのはこの指令量にあたる波形で、「実際の目標 − 計画」として作る。

AEMOとERCOTには基準値と指令量を分ける仕組みがないので、次のように対応づける。GBのBalancing Mechanismには二次②と同じ構造があり、そのまま対応する。

| 二次② | AEMO 蓄電池 | ERCOT ESR | GB 蓄電池 |
|---|---|---|---|
| 基準値 | AEMOがそのユニットの入札から計算した予定出力（PREDISPATCH） | 事業者（QSE）が出した運転計画（COP）の計画SOCから出した、1時間ごとの計画出力 | 事業者が出した出力計画のうち、ゲートクローズ時点の値（FPN） |
| 基準値を固定する時点 | 5分区間の終わりの中央値16分前（長期データ）、46分前（60日分） | 各時間の開始1時間前（2026-03-10の全7,464件で確認） | 30分コマの開始1時間前（日本と同じ） |
| 指令量 | TOTALCLEARED − PREDISPATCH | SCED Base Point − 計画出力 | その時点で有効な最新のBOAの水準 − FPN。有効なBOAがなければ0 |
| 幅 | ユニットの利用可能量の最大値 | オンライン中の max(HSL, −LSL) の最大値 | 登録容量 max(発電, \|需要\|) |

BOA（Bid-Offer Acceptance）は、GBの系統運用者（NESO）がゲートクローズ後にユニットへ出す出力変更の指示で、水準の時系列として公開される。

どれも、指令量をユニットごとの固定幅で割る。時刻ごとに変わる値では割らず、生成時にclipもしない。幅を超えた値は入札器の入力でclipする。

ERCOTのCOPにはESRのMW計画がなく、各時間の開始時点の計画SOCだけがある。その時間の計画出力は、計画SOCの減り分（放電を正）とする。SCEDのSOCと出力の実測では、約55分間のSOCの変化が −0.91 × 出力だったので、MWhとMWをほぼ1対1で換算する。

## 指令集合

`EVMA_ACTIVATION_SIGNAL_SET` で選ぶ。集合どうしは混ぜず、bankも別々に作る。bankには指令ファイルのhashが入るので、別の集合のbankは混用されない。

| 値 | 中身 | 用途 |
|---|---|---|
| `aemo_plan_deviation`（既定） | AEMO 蓄電池52資源の計画からのずれ。約16分前の計画。10,905本、2025-08〜2026-07 | 主な指令 |
| `aemo_plan_deviation_gc` | 同じ変換で、55分以上前の最後のPREDISPATCHを計画にしたもの。2,495本、2026-07〜09の60日分 | 計画の時点の影響の確認 |
| `ercot_plan_deviation` | ERCOT ESR 299基のBase Point − COP計画出力。46,994本、2025-12〜2026-07 | 第2の指令集合 |
| `elexon_plan_deviation` | GB 蓄電池15基のBOA − FPN。trainの日に指示の多かった上位20基から、SOフラグ付きの指示が過半の5基を除いた。4,305本、2025-12〜2026-09 | 第3の指令集合 |
| `aemo_bess_dispatch` | AEMO 蓄電池8資源のTOTALCLEAREDそのもの。0 MWを基準にし、その日の最大の絶対値で割る。2,277本 | EV-VPPが成立しない条件の説明 |
| `nem` | 計画からのずれを、時刻ごとの利用可能量で割って[0, 1]にclipしたもの | 旧実験の再現 |
| `aemo_wdru` | AEMO WDRUの需要削減目標。0を基準とする | 補助。イベント日が15日しかない |
| `ercot` | ERCOT Base Pointを連続オンライン区間の先頭からの差にしたもの。未生成 | 旧定義 |
| `pjm_regd` | PJM の調整力信号 RegD（Dynamic）の5分点ごとの値。363本、2024-03〜2025-02 | AGC型の比較の最終評価（validationとtestの日だけ） |
| `pjm_regd_phase_shift` | `pjm_regd` のtrainの日から、5分点を取る時刻を0〜290秒ずらして作った疑似指令。6,390本 | AGC型の比較の入札と学習 |

`aemo_bess_dispatch` の1日は、中央値56%が休止で、残りは数時間続く充電・放電になる。学習や通常の評価には使わない。

## 区分

暦日単位でtrain / validation / testに分け、同じ日を複数の区分で使わない。入札設計（forecast）はtrainだけを使う。下位のMARLは、train以外（validationとtest）から、エピソードごとに1本ずつランダムに引いて学習する。最終評価（holdout）はtestから引き、学習中に引いた指令は除く。学習中に引いた指令は、乱数の種とエピソード番号から割り出す。

どの集合も暦月ごとに、月の初めから連続した60/20/20の日に分ける。どの区分にも同じ月が入るので、季節の混ざり方が区分どうしでそろう。上げの割合は季節で変わることがある（二次②との違いを参照）。

- `aemo_plan_deviation`：train 6,353本、validation 2,242本、test 2,310本（2025-08-02〜2026-07-30）
- `aemo_plan_deviation_gc`：train 1,411本、validation 525本、test 559本（2026-07-13〜09-09）
- `ercot_plan_deviation`：train 26,389本、validation 9,841本、test 10,764本（2025-12-06〜2026-07-24）。幅を超えた値は全stepの0.8%
- `elexon_plan_deviation`：train 2,520本、validation 855本、test 930本（2025-12-01〜2026-09-14）。幅を超えた値は全stepの1.2%
- `aemo_bess_dispatch`：train 1,320本、validation 465本、test 492本
- `pjm_regd`：train 213本、validation 72本、test 78本（2024-03-01〜2025-02-28）。幅を超えた値は全stepの5.8%
- `pjm_regd_phase_shift`：train 3,570本、validation 1,380本、test 1,440本（`pjm_regd` のtrainの213日を、暦月ごとに60/20/20で分け直し、1日30本）

発動中のうち上げの割合の中央値は、区分ごとにAEMO 47〜48%、ERCOT 44%、GB 51〜54%だった（`python tools/command_library_shape_stats.py`）。

## 指令の形

各集合から2,000本を抜き出し、同じ定義で数えた（中央値 / 90パーセンタイル）。|a| > 0.01 のstepを発動中とし、aは幅で割った指令量（上げが正）。

| | `aemo_plan_deviation` | `ercot_plan_deviation` | `elexon_plan_deviation` |
|---|---|---|---|
| 発動中のstepの割合 | 0.25 / 0.49 | 0.59 / 0.89 | 0.30 / 0.48 |
| 同じ向きが続いた最長step数 | 11 / 22 | 34 / 61 | 14 / 30 |
| 向きが変わった回数 | 11.5 / 28 | 9 / 22 | 4 / 9 |
| \|a\| の平均 | 0.08 / 0.18 | 0.13 / 0.27 | 0.12 / 0.23 |
| 累計エネルギー偏差の最大（幅×時間） | 0.68 / 1.78 | 0.94 / 2.01 | 1.78 / 4.70 |
| 発動中のうち上げの割合 | 0.47 / 0.70 | 0.44 / 0.59 | 0.52 / 0.98 |

GBは3集合のなかで、向きの変わる回数が最も少なく、累計エネルギー偏差が最も大きい。集計は `python tools/command_library_shape_stats.py`。

## 二次②との違い

- AEMOとERCOTの集合は、エネルギー市場で5分ごとに解き直した配分の変化であり、調整力の発動分ではない。AEMOのAGC設定値は公開されていない。
- どの集合も1つの資源が受けた配分の変化や指示であって、送配電事業者がアグリゲーターに出す指令ではない。日本の二次②では、送配電事業者がkWh価格の安い順に稼働指令を出す（需給調整市場ガイドライン）。
- AEMOの基準値は事業者の計画ではなく、AEMOの予定出力である。固定する時点も日本のゲートクローズ（5分区間の終わりから65〜90分前）より直前になる。同じユニット・同じ日の786件で比べると、46分前の計画からのずれは16分前の計画からのずれより、平均の絶対値で1〜2割大きかった。
- ERCOTの基準値は事業者自身の計画で、固定する時点も日本と同じだが、1時間ごとの値しかない。計画出力と1時間平均のBase Pointの相関は0.29で、最後の更新は時間の開始の中央値で約17時間前だった（2026-03-10）。指令量には、市場の再配分に加えて計画の古さや外れも含まれる。
- GBの基準値は事業者自身の計画で、固定する時点も日本と同じ。BOAは系統運用者の指示だが、需給調整のほかに系統制約の解消にも使われる。SOフラグ（需給調整以外の理由で出された可能性があることを示す印）の付いた指示が過半のユニットは除いた。上位20基のうち5基（T_BLHLB-1〜3、E_JAMBB-1・2）がこれにあたり、SOフラグ付きの割合は52〜70%だった。残した15基では、SOフラグ付きのBOAは指示のあるstepの0.2%。
- GBの集合は指示の多いユニットを選んだもので、GBの蓄電池全体を代表しない。
- GBの上げの割合は季節で変わる。15基では、12〜3月に56〜79%、5〜8月に31〜41%だった。区分を月ごとに分けるのはこのため。
- どの集合も蓄電池の指令である。

## 採らなかった方法と理由

| 方法 | 採らなかった理由 |
|---|---|
| 目標値そのもの（AEMO TOTALCLEARED、ERCOT Base Point） | 資源自身の充放電計画が指令に入り、EV-VPPの基準値の上に二重に足される。AEMOは説明用（`aemo_bess_dispatch`）として残す |
| 日初の値を基準にする | 00:05の充放電が1日中の基準になり、止まっただけで持続的な発動になる。累計エネルギー偏差が4帯幅時間以上の185日のうち156日がこれにあたった |
| 時刻ごとの利用可能量で割ってclipする（`nem`） | 割る値が時刻ごとに変わるので波形の大きさが歪み、1を超える分が切れる |
| 1日の最大値で割る | 動きの小さい日も必ず満幅まで拡大される |
| ERCOT SCEDのOutput Schedule | ON状態のESRでは全行0だった。ONOS状態のESRはなかった（2026-03-10） |
| ERCOT DAMの約定量 | 0でない約定を持つESRが311基中116基、行の8%だけだった（2026-03-10） |
| ERCOTのRTC+B以前の5分データ | 公開されているのは15分ごとの1点だけ |
| ERCOTのRTD indicative base point | QSE限定の非拘束の値で、公開されていない |
| AEMOのゲートクローズ時点の計画を長期で使う | 全実行が残るのは直近60日分だけで、長期のアーカイブには1期間1実行しか残らない |
| GBの蓄電池を選ばずに全部使う | 候補284基のうち143基は、trainから抜き出した24日に一度も指示を受けておらず、ほぼ0の日が並ぶ |
| 時系列順に60/20/20で分ける | 区分ごとに季節が変わる。GBではtrainが冬、validationとtestが夏になり、上げの割合（中央値）がtrain 47%、validation 20%、test 15%とずれた（SOフラグの多い5基を含む旧集合）。AEMOではtestが2026-05-20〜07-30だけになった |
| GBのSOフラグ付きBOAを除く | 除いた時刻には、そのBOAが上書きした古い指示かFPNの値が残り、ユニットが実際に指示された水準と食い違う |
| GBのBid-Offer Dataや出力上限の申告値（MEL/MIL）で割る | 時刻ごとに変わる値で割ることになる（`nem` と同じ理由） |
| 日本の二次②の実指令 | 一般公開されていない |

## ERCOTの取得

API認証（email、password、subscription key）は実行者が入力する。コードやmanifestには保存しない。
既定の終了日は実行日の60日前。中断後は同じコマンドで再開する。

```powershell
# SCED（NP3-965-ER）。CLR・ESRのBase Point、HSL/LSLなど必要な列だけ残す
.\ercot_local_downloader\run_all_windows.bat
# COP調整期間スナップショット（NP1-301）。ファイルをそのまま残す
.\ercot_local_downloader\run_cop_windows.bat
```

保存先は `ercot_local_downloader/ercot_sced_rtc_output/` と `ercot_local_downloader/ercot_cop_snapshot_output/`。どちらも2025-12-05（RTC+B開始）以降が対象。

## ERCOTの整形（`ercot_plan_deviation`）

```powershell
python tools/build_ercot_plan_deviation_library.py
```

1. 同じresource・同じ実行時刻の訂正は公開日が新しいほうを使う。
2. 現地時刻はAmerica/Chicago。23時間・25時間の日は除く。
3. 5分点tには `(t−5分, t]` の最新の実行だけを使う。空の窓は補間せず、その日を除く。
4. 288点すべてがオンライン（ON/ONREG/ONRR/ONRRREG）の日だけを使う。未知のstatusを含む日は除く。
5. 翌日0時の計画SOCまで25時間分そろった日だけを使う。同じ時間に食い違う計画SOCがある場合は、その時間を欠けたものとする。

## GBの取得と整形（`elexon_plan_deviation`）

Elexon Insights APIを使う。APIキーは要らない。取得はユニットごとに再開できる。

```powershell
python tools/build_elexon_plan_deviation_library.py
```

1. 候補は、Elexonの参照データで燃料種別がOTHERか空欄で、発電と需要の容量がともにあり、その比が0.5〜2倍のユニット（284基）。参照データに蓄電池の燃料種別はなく、この条件で揚水（PS）と一方向のユニットを除く。
2. trainの日を7日おきに24日抜き出し、BOAが有効な5分点の割合が大きい20基を選ぶ（30〜39%）。そのうち、指示のある5分点の過半にSOフラグが付くユニットを除く。validationとtestの日は見ない。
3. 残った15基のBOAとPN（事業者の出力計画）を全期間取る。
4. 5分点tのFPNは、tを含むPNの値。BOAは、tまでに出され、tを含む最新のもの。どちらもElexonの形式どおり区間内を直線でつなぐ。
5. 現地時刻はEurope/London。23時間・25時間の日は除く（15ユニット日）。FPNが欠けた日はなかった。

保存先は `data/elexon/plan_deviation_raw/`（取得したBOAとPN、選定結果）と `data/elexon/command_libraries/battery_plan_deviation_calendar_day/`。

## PJMの取得と整形（`pjm_regd`）

PJMが公開している RTO Regulation Signal Data（`https://www.pjm.com/-/media/DotCom/markets-ops/ancillary/rto-regulation-signal-data.ashx`、zip）を使う。2026-10-03 時点の中身は2024-03〜2025-02の12か月分で、それより前の年の公開ファイルは見つからなかった。各月のExcelに、2秒ごとのRegD（`Dynamic`）とRegA（`Traditional`）のシートがある。保存先は `data/input.demand_fromPJM/`。

```powershell
python tools/build_pjm_regd_library.py --mode real          # pjm_regd
python tools/build_pjm_regd_library.py --mode phase_shift   # pjm_regd_phase_shift
```

1. RegDは資源の調整幅で正規化された信号（−1〜1、上げが正）なので、固定幅は1とする。ただし公開値には±1を少し超える点があり（最大1.11）、5分点のうち実指令で約5.8%、疑似指令で約6.9%が±1を超える。ほかの集合と同じく、入札器の入力で1に切る。
2. 各日の 00:00, 00:05, …, 23:55 ちょうどの2秒値を取る。ほかの集合と同じく、その5分点で有効な値で、平均はしない。
3. 夏時間の切り替え日（2024-03-10、2024-11-03）は除く。
4. 暦月ごとに、月の初めから連続した60/20/20の日に分ける。

保存先は `data/pjm/command_libraries/regd_calendar_day/`。

### 実指令を評価にだけ使う理由

PJMの信号は系統全体で1本なので、1日に指令が1本しかない。validationとtestを合わせても150本で、ほかの集合と同じくそこから学習の指令を引くと、2000回の学習でほぼすべてを引き、最終評価に使える未見の指令が残らない。
そこで、実指令（`pjm_regd`）のvalidationとtestの日は、最終評価にだけ使う。入札と学習（学習の途中テストを含む）は、trainの日だけから作った疑似指令（`pjm_regd_phase_shift`）を使う。

1. trainの213日について、5分点を取る時刻を0, 10, …, 290秒ずらして288点を取る（1日30本）。0秒は実指令そのもの。
2. 元のtrainの日を暦月ごとに連続した60/20/20で分け直し、trainを入札の設計に、validationとtestを学習で引く指令にする。入札の設計と学習で、元の日が重ならない。
3. validationとtestの日の信号は読まないので、評価する日の情報は入札にも学習にも入らない。

ほかの集合は実指令で入札と学習をしているので、PJMだけ条件が違う。疑似指令と実指令の形の差（中央値。疑似指令はずらし10〜290秒の6,177本、実指令はvalidationとtestの150日）：

| | 疑似指令 | 実指令（評価） |
|---|---:|---:|
| 発動中の5分点の割合 | 0.99 | 0.99 |
| 同じ向きが続いた最長step数 | 8 | 8 |
| 向きが変わった回数 | 132 | 137 |
| \|a\| の平均 | 0.558 | 0.559 |
| 累計エネルギー偏差の最大（幅×時間） | 1.14 | 1.36 |
| 発動中のうち上げの割合 | 0.48 | 0.47 |

累計エネルギー偏差の最大だけ、疑似指令のほうが小さい。

RegAは、この期間は下げに偏っていた（発動中の上げの割合の中央値27%、累計エネルギー偏差の最大の中央値は幅の9倍・時間）。エネルギー収支が小さいとは言えないので使わない。

PJMは2025年10月に調整力を1本の双方向の商品にまとめた。それ以降の信号の実データは公開されていない（1日分のサンプルだけ）。
